# ADR-0002：LLVM 优先编译与自建商用运行时

- 状态：已接受
- 日期：2026-09-03
- 决策于：openspec 变更 `ratify-language-foundations`

## 背景

spec v0.8（私有参考，`refr/spec-0.8.md`）曾以编译到 Go 的方式实现过一次 demo。项目目标其后升级为**可商用交付的语言产品**——编译器与运行时皆为产品——对性能、效率、资源占用做极致追求。demo 时代的宿主策略（Go 后端、`foreign "go"`、`runtime.We*` 类型映射表）封住了这个目标：精确 GC、尾调用与优化上限都被宿主运行时模型限定。

## 决策

1. **从第一天起面向 LLVM IR。** 编译器发射 LLVM IR，经 LLVM 后端产出原生二进制；工具链以钉住 LLVM 版本为纪律。不引入 C 源码中间层。
2. **运行时是产品范围，不是代价。** 自建，包含完整 GC 机制（精确回收）、调度器、I/O 多路复用与规范定义的并发原语。
3. **编译器实现语言 v1 保持 Go，与编译目标解耦。** 以文本 IR 发射并驱动 LLVM 工具链；实现语言永远不约束编译目标。远期里程碑：**自举**——语言稳定到可引导后，用 We 重写编译器（用户裁决，2026-09-03）。规范正典刻意不点名实现语言，只承载解耦纪律。
4. **FFI 为 `foreign "c"`**——C ABI 上的受控互操作边界，接受完整的类型、effect、所有权检查。如未来需要 Go 生态互操作，经 C 桥另作决策。
5. **规范纪律：机制中性。** 规范以自身术语定义可观察语义与保证。精确 GC、暂停预算、尾调用行为是由运行时承载、以基准度量的实现质量目标；仅经显式 spec 层变更才可升格为规范承诺。

## 依赖

产品依赖一个刻意保持小而明确枚举的三方件集合，每个都钉住版本（用户指示，2026-09-03）：

| 组件 | 角色 | 钉住方式 |
| --- | --- | --- |
| LLVM **21.1.8** | IR 目标与原生后端（`opt` / `llc` / `lld`） | 精确版本；升级是显式的 tooling 层变更 |
| clang / clang++（出自钉住的 LLVM 21.1.8） | 编译运行时的 C/C++ 源码 | 与 LLVM 同一版本钉住；运行时以预编译产物（目标文件/bitcode）随工具链分发，We 用户无需 C 工具链（用户裁决，2026-09-03） |
| Go 工具链 | 编译器实现语言（v1；远期里程碑为自举） | 编译器启动时经 `go.mod` toolchain 指令钉住；权威钉住值在那里，不在本 ADR |
| 平台 libc / C ABI | FFI 边界与运行时链接 | 按目标平台；支持矩阵在运行时落地时决定 |

钉住规则：

- 权威的活版本值在编译器仓库结构落地时迁移到工具链版本清单；本 ADR 记录纪律与初始钉住值，不承载活值。
- 规范正典（`docs/spec/`）永不携带版本号——可观察语义以语言自身术语定义（第 0 章机制中性纪律）。版本变更触及清单与 ADR，永不触及规范正文。
- 除上述外无其他三方运行时依赖：运行时按决策 2 自建。

## 后果

- 运行时（GC、调度器、netpoll、原语）成为长期工程承诺，有自己的 roadmap；这是为商用目标明确接受的成本。
- 评估方法论（First-Pass Compile Rate 等）的重心保持在前端与诊断闭环（`we check` 不依赖代码生成）。
- v0.8 的宿主特定内容（`foreign "go"`、`runtime.We*` 映射表）降级为反例参考。

## 被拒替代方案

- **保留 v0.8 的 Go 后端：** 最快的路径（demo 已证明），但封顶精确 GC、尾调用与优化余量——与商用目标不兼容（用户裁决，2026-09-03）。
- **C 源码作为中间层：** 可移植、可调试，但同样的封顶问题下沉一层——精确栈扫描、零成本尾调用、细粒度优化仍然受阻；且 C 编译增加一个工具链阶段，却不能把 LLVM 从最终路径上移除。经用户裁决拒绝（2026-09-03）。
- **用 gcc 构建运行时 C/C++ 源码：** 引入第二条工具链家族与独立版本线；无 LLVM bitcode 与跨链接 LTO；交叉编译需逐目标配工具链；其优势场景（冷门/嵌入式平台）在批准的目标场景之外；GPLv3 对商用工具链不如 LLVM 宽松许可友好。被拒，改用钉住家族的 clang（2026-09-03）。
