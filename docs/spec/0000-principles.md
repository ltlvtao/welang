# We Language Specification — Chapter 0: Foundations and Principles

### Requirement: Target profile

We is a general-purpose **backend language**. Its ratified target domains are: HTTP/RPC services, background job processing, CLI tools, and data pipelines. We is explicitly NOT a systems-programming language: kernels, drivers, embedded targets, game engines, and HPC kernels are out of profile. This narrowing is the root premise of every tradeoff in this specification: We forgoes systems-programming flexibility (manual memory layout, operator overloading, unrestricted generic variance) in exchange for correctness and maintainability in backend scenarios.

#### Scenario: Out-of-profile feature is proposed

- **WHEN** a proposal adds manual memory-layout control or another systems-programming capability
- **THEN** it MUST be rejected as out of profile unless it first amends this Requirement through a spec-layer change

#### Scenario: Profile is used as an arbitration premise

- **WHEN** a design dispute asks whether We should adopt a capability that serves systems programming at the cost of backend correctness or maintainability
- **THEN** the dispute resolves against adoption, citing this Requirement

### Requirement: First-class author and core loop

We's first-class author is a large language model operating in a **generate–check–fix loop**. The compiler is the adjudicator of that loop; humans audit results and make decisions. All three parties are first-class consumers of the language surface:

- The program text is written to be generated by models and read by reviewers — local reasoning about validity, not brevity of keystrokes, is the optimization target.
- The diagnostics protocol (human-readable and machine-readable forms) is the primary interface of the loop and a stability commitment of this specification.
- Local checkability (Principle 1) ranks above all other principles because the loop must generate and verify code from local context alone.

#### Scenario: Brevity is traded against local checkability

- **WHEN** a feature proposal shortens program text by making validity depend on non-local information
- **THEN** the proposal conflicts with this chapter's Principle 1 and MUST be rejected or reworked to restore local checkability

#### Scenario: A tool omits machine-readable diagnostics

- **WHEN** a tool in the `we` toolchain reports a diagnosable condition in a human-readable form only
- **THEN** it violates the loop contract: the condition MUST also be reported through the machine-readable diagnostics form, unless infeasibility is explicitly recorded as Principle 7 allows

### Requirement: Principle 1 — Local reasonability over global optimality

The validity of any function or type definition MUST be decidable from its own signature and the definitions it directly references. Validity MUST NOT depend on call-site information, global program state, or "who will call this in the future". This is what allows both models and humans to generate or verify a code fragment with high confidence from local context alone, without loading a whole project.

Exception: a project-level build configuration file counts as fixed context, provided its influence on validity is limited to diagnostic-level behavior and never alters the outcome of type checking, effect checking, or ownership checking.

#### Scenario: Call-site-dependent validity is proposed

- **WHEN** a feature proposal makes a definition legal or illegal depending on its future callers (for example, inferring a function contract from call sites)
- **THEN** the proposal MUST be rejected under this Principle

### Requirement: Principle 2 — Unique semantics over expressiveness

Each semantic goal (for example: string formatting, error signaling, resource release, sharing state across tasks) MUST have exactly one way to be written. Where two paths are genuinely necessary, the split between them MUST be governed by a mechanically decidable rule that does not depend on taste.

Exception: notations borrowed from an external ecosystem standard (for example, semver constraint operators) do not violate this Principle when each notation denotes a distinct semantic that itself has no duplicate path.

#### Scenario: A second path for an existing semantic is proposed

- **WHEN** a proposal introduces a second way to express a semantic that the specification already covers
- **THEN** it MUST either be rejected or accompanied by a mechanically decidable division rule between the two paths

#### Scenario: Division rule is subjective

- **WHEN** the proposed division between two paths depends on style preference or judgment rather than a machine-decidable criterion
- **THEN** the two-path proposal MUST be rejected under this Principle

### Requirement: Principle 3 — Decidability over expressiveness

When a candidate feature could make type inference or checking complexity unbounded (for example: unrestricted generics, a macro system, arbitrary variance), the language MUST either set an explicit, fixed bound on it or reject it. Complex algorithms MUST NOT be admitted as a fallback to rescue undecidable or unstable behavior.

#### Scenario: An unbounded-expressiveness feature is proposed

- **WHEN** a proposal admits a feature whose checking complexity has no fixed bound and proposes "smarter inference" as the mitigation
- **THEN** the proposal MUST be rejected or reworked with an explicit bound under this Principle

### Requirement: Principle 4 — Ambiguity elimination over flexibility

Any syntactic structure that admits two or more reasonable interpretations MUST be rejected by the compiler with a diagnostic; the compiler MUST NOT silently choose a default interpretation. Context-sensitive lexing MUST NOT be introduced; if any strictly bounded exception exists, it MUST be enumerated in the lexical chapter of this specification and closed to further additions.

#### Scenario: An ambiguous construct appears

- **WHEN** a token sequence admits two distinct parses and both are defensible readings
- **THEN** the compiler MUST report an ambiguity diagnostic naming the competing interpretations instead of compiling either one

### Requirement: Principle 5 — Explicitness over implicitness

Type conversions, side effects, resource release, and error propagation MUST each leave a visible trace in the syntax. Code whose behavior "cannot be seen to happen" from its local text MUST NOT exist. Any implicit conversion, to be admissible at all, MUST be anchored to a single explicit syntactic marker, be mechanically decidable, and be unambiguous — and the set of such conversions MUST be closed (no new ones without amending this specification).

#### Scenario: An implicit conversion is proposed

- **WHEN** a proposal adds a conversion that takes effect without an explicit syntactic anchor
- **THEN** it MUST be rejected under this Principle

#### Scenario: A conversion is anchored but multiplies

- **WHEN** a conversion is anchored to an explicit marker but the proposal opens a class of conversions rather than one closed, enumerated case
- **THEN** it MUST be rejected under this Principle

### Requirement: Principle 6 — Static decidability over runtime flexibility

Type checking, effect checking, ownership checking, and exhaustiveness checking MUST be performed at compile time by deterministic algorithms. Heuristics MUST NOT be used to guess a program into passing these checks; a check either proves the property or fails with a diagnostic.

#### Scenario: A heuristic pass is proposed

- **WHEN** an implementation or proposal suggests admitting a program that a deterministic check cannot prove correct, on the grounds that it "usually works"
- **THEN** it MUST be rejected under this Principle

### Requirement: Principle 7 — Toolchain consistency and machine operability

The toolchain MUST provide a mandatory formatter with no configuration options, so that surface style is single-sourced and never a source of diff noise; and every compiler diagnostic MUST be provided, wherever feasible, with a structured, machine-operable remediation description in addition to its human-readable form. Both human and model authors depend on a consistent surface and actionable feedback to complete the generate–check–fix loop.

#### Scenario: Formatter configurability is proposed

- **WHEN** a proposal adds formatting options (line length, style presets, and the like) to the official formatter
- **THEN** it MUST be rejected under this Principle

#### Scenario: A diagnostic ships without a machine-operable form

- **WHEN** a new diagnostic is specified only as prose for humans
- **THEN** the specification MUST additionally define its machine-readable fields or explicitly record why that is not feasible

### Requirement: Principle 8 — No escape hatches at language boundaries

Any mechanism that crosses a language boundary or bypasses the type system (foreign-function interfaces, reflection, an attribute system) MUST remain subject to the same degree of static checking as ordinary code. "It is native code", "it is metaprogramming", or "it is only an annotation" MUST NOT exempt code from type, effect, or ownership checking. An attribute mechanism, if present, MUST NOT influence the results of type checking, effect checking, or ownership checking.

#### Scenario: An unchecked boundary is proposed

- **WHEN** a proposal allows calling foreign code without effect and ownership annotations, or reflects over values in a way the type system cannot check
- **THEN** it MUST be rejected under this Principle

### Requirement: Principle 9 — A single error mechanism

Errors MUST flow through exactly one signaling and propagation mechanism in the language. Parallel channels — exceptions, implicit panic propagation, or a separate failure path "just for concurrency" — MUST NOT exist. Concurrency-related failures (timeouts, cancellation, task-internal panics) use the same mechanism as every other failure. The concrete mechanism is defined by the error-handling chapter of this specification.

#### Scenario: A parallel failure channel is proposed

- **WHEN** a proposal introduces exceptions or any second error-propagation path, including one scoped to concurrent tasks
- **THEN** it MUST be rejected under this Principle

### Requirement: Principle 10 — Completeness closure over speculative design

A feature entering this specification MUST arrive with complete designs for checking, code generation, and runtime behavior. A construct that the parser accepts but the code generator does not, or that checks but has no runtime story, MUST NOT be ratified into the specification. Half-finished features do not ship in anticipation of future completion.

#### Scenario: A partial feature seeks ratification

- **WHEN** a proposal defines syntax and checking for a construct but leaves code generation or runtime behavior undefined
- **THEN** the proposal MUST be held back from ratification until all three elements are specified

### Requirement: Priority order and tie-breaking

The ten Principles form a strict priority order: 1 local reasonability, 2 unique semantics, 3 decidability, 4 ambiguity elimination, 5 explicitness, 6 static decidability, 7 toolchain consistency and machine operability, 8 no escape hatches, 9 single error mechanism, 10 completeness closure. When two Principles conflict in the evaluation of a proposal, the higher-ranked Principle wins. Deviating from a Principle, or from this order, requires explicit justification in the proposal's `## Why` and an ADR recording the exception.

#### Scenario: Principles conflict in a proposal

- **WHEN** a proposal improves explicitness (Principle 5) but only at the cost of local checkability (Principle 1)
- **THEN** Principle 1 prevails and the proposal MUST be reworked or rejected, with any exception requiring an ADR

### Requirement: Host and compilation target strategy

We is delivered as a commercial language product: compiler and runtime are both product surfaces, with an extreme pursuit of performance, efficiency, and resource footprint. The ratified platform commitments are:

- The compiler emits **LLVM IR from day one** and produces native binaries through LLVM backends; the toolchain pins LLVM versions as a discipline.
- The runtime is self-built and is product scope, not an implementation detail: it includes a complete garbage-collection mechanism (precise reclamation), a scheduler, I/O multiplexing, and the concurrency primitives defined by this specification.
- The compiler implementation language is an engineering choice, decoupled from the compilation target and from language semantics; the compiler emits textual IR and drives LLVM tooling.
- The foreign-function interface is `foreign "c"`: a controlled interoperation boundary at the C ABI, subject to full type, effect, and ownership checking (Principle 8).
- This specification defines observable semantics and guarantees on its own terms. Precision of GC, pause budgets, and tail-call behavior are implementation-quality goals carried by the runtime and measured by benchmarks; they become specification commitments only through an explicit spec-layer change.

#### Scenario: Language behavior is defined through a backend mechanism

- **WHEN** a proposal defines an observable language behavior in terms of LLVM mechanics, GC implementation, or runtime internals
- **THEN** it MUST be reworded to define the observable behavior on its own terms, or rejected

#### Scenario: A boundary weakens checking

- **WHEN** a proposal requires escaping type, effect, or ownership checks at the `foreign "c"` boundary for convenience or performance
- **THEN** it MUST be rejected under Principle 8 as read through this Requirement
