# We 语言规范 —— 第 0 章：基础与原则

### Requirement: 目标场景

We 是一门通用**后端语言**。其批准的目标域为：HTTP/RPC 服务、后台任务处理、CLI 工具、数据管道。We 明确不是系统编程语言：内核、驱动、嵌入式目标、游戏引擎、HPC 内核均在场景之外。这一收窄是本规范一切取舍的根前提：We 放弃系统编程的灵活性（手工内存布局、运算符重载、不受限的泛型变型），换取后端场景下的正确性与可维护性。

#### Scenario: 提出场景外特性

- **WHEN** 某提案加入手工内存布局控制或其他系统编程能力
- **THEN** 必须以"场景外"为由拒绝，除非该提案先通过 spec 层变更修订本条 Requirement

#### Scenario: 目标场景被用作裁决前提

- **WHEN** 某设计争议问 We 是否应采纳一项以牺牲后端正确性或可维护性为代价、服务于系统编程的能力
- **THEN** 争议裁定为不采纳，并引用本条 Requirement

### Requirement: 第一作者与核心循环

We 的第一作者是在**生成—检查—修复循环**中工作的大语言模型。编译器是该循环的裁决者；人类审计结果并作出决定。三方都是语言表面的第一等消费者：

- 程序文本为"由模型生成、由评审者阅读"而写——优化目标是合法性的局部可推理，而非击键简洁。
- 诊断协议（人类可读与机器可读两种形态）是循环的主接口，是本规范的稳定性承诺。
- 局部可检查性（原则 1）位居所有原则之上，因为循环必须仅凭局部上下文就能生成并验证代码。

#### Scenario: 以局部可检查性换取简洁性

- **WHEN** 某特性提案通过让合法性依赖非局部信息来缩短程序文本
- **THEN** 该提案与本第 0 章的原则 1 冲突，必须拒绝或重做到恢复局部可检查性

#### Scenario: 工具缺失机器可读诊断

- **WHEN** `we` 工具链中的某工具仅以人类可读形态报告一个可诊断情形
- **THEN** 它违反了循环契约：该情形必须同时经机器可读诊断形态报告，除非按原则 7 的允许显式记录了不可行原因

### Requirement: 原则 1 —— 局部可推理性优先于全局最优

任何函数或类型定义的合法性必须可由其自身签名与其直接引用的定义判定。合法性不得依赖调用点信息、全局程序状态或"未来谁会调用我"。这使模型与人类都能仅凭局部上下文、无需加载整个项目，对代码片段的生成或验证持有高置信度。

例外：项目级构建配置文件计为固定上下文，前提是它对合法性的影响限于诊断级行为，且永不改变类型检查、效应检查、所有权检查的结果。

#### Scenario: 提出依赖调用点的合法性

- **WHEN** 某特性提案让一个定义合法与否取决于其未来调用者（例如从调用点推断函数契约）
- **THEN** 该提案必须依本原则拒绝

### Requirement: 原则 2 —— 唯一语义优先于表达力

每个语义目标（例如：字符串格式化、错误通知、资源释放、跨任务共享状态）必须恰好有一种写法。当两条路径确属必要时，二者的划分必须由不依赖品味、机械可判定的规则治理。

例外：借自外部生态标准的记法（例如 semver 约束运算符）在其每个记法各指称一个本身无重复路径的独立语义时，不违反本原则。

#### Scenario: 为既有语义提出第二条路径

- **WHEN** 某提案为规范已覆盖的语义引入第二种表达方式
- **THEN** 必须拒绝，或附带两条路径之间机械可判定的划分规则

#### Scenario: 划分规则是主观的

- **WHEN** 两条路径之间的拟议划分依赖风格偏好或判断，而非机器可判定的标准
- **THEN** 该双路径提案必须依本原则拒绝

### Requirement: 原则 3 —— 可判定性优先于表达力

当候选特性可能使类型推断或检查复杂度无界（例如：不受限的泛型、宏系统、任意变型）时，语言必须对它设置显式固定上限，或拒绝它。不得以复杂算法作为挽救不可判定或不稳定行为的兜底。

#### Scenario: 提出无界表达力特性

- **WHEN** 某提案接纳一个检查复杂度无固定上限的特性，并以"更聪明的推断"作为缓解
- **THEN** 该提案必须拒绝，或依本原则重做为带显式上限的形态

### Requirement: 原则 4 —— 消除歧义优先于保留灵活性

任何存在两种及以上合理解释的语法结构，必须由编译器以诊断拒绝；编译器不得静默选择默认解释。不得引入上下文敏感的词法；若存在严格有界的例外，必须在本规范的词法章节中枚举，并对进一步 additions 关闭。

#### Scenario: 出现歧义构造

- **WHEN** 某 token 序列存在两种不同语法分析且两种读法皆可辩护
- **THEN** 编译器必须报告点名竞争解释的歧义诊断，而非编译其中任何一种

### Requirement: 原则 5 —— 显式优先于隐式

类型转换、副作用、资源释放、错误传播必须各自在语法中留下可见痕迹。"从局部文本上看不见其发生"的代码不得存在。任何隐式转换若要被接纳，必须锚定于单一显式语法标记、机械可判定且无歧义——且此类转换的集合必须是闭集（不修订本规范不得新增）。

#### Scenario: 提出隐式转换

- **WHEN** 某提案加入一个无显式语法锚点即生效的转换
- **THEN** 必须依本原则拒绝

#### Scenario: 转换有锚点但扩散

- **WHEN** 某转换锚定于显式标记，但提案开启的是一类转换而非一个封闭枚举的个例
- **THEN** 必须依本原则拒绝

### Requirement: 原则 6 —— 静态可判定性优先于运行时灵活性

类型检查、效应检查、所有权检查、穷尽性检查必须在编译期由确定性算法完成。不得用启发式把程序"猜"过这些检查；检查要么证明性质成立，要么以诊断失败。

#### Scenario: 提出启发式放行

- **WHEN** 某实现或提案建议以"通常没问题"为由，接纳确定性检查无法证明正确的程序
- **THEN** 必须依本原则拒绝

### Requirement: 原则 7 —— 工具链一致性与机器可操作性

工具链必须提供强制且零配置选项的格式化器，使表面风格单一来源、永不成为 diff 噪声；且每个编译器诊断在可行的范围内，除人类可读形态外必须附结构化、机器可操作的修复描述。人类与模型作者都依赖一致的表面与可执行的反馈来完成生成—检查—修复循环。

#### Scenario: 提出格式化器可配置性

- **WHEN** 某提案为官方格式化器加入格式化选项（行宽、风格预设等）
- **THEN** 必须依本原则拒绝

#### Scenario: 诊断不带机器可操作形态

- **WHEN** 某新诊断仅以面向人类的散文形态定义
- **THEN** 规范必须补充定义其机器可读字段，或显式记录为何不可行

### Requirement: 原则 8 —— 语言边界不留逃生舱

任何跨语言边界或绕过类型系统的机制（外部函数接口、反射、属性系统）必须与普通代码受同等程度的静态检查。"它是原生代码"、"它是元编程"、"它只是个注解"不得使代码豁免类型、效应、所有权检查。属性机制（若存在）不得影响类型检查、效应检查、所有权检查的结果。

#### Scenario: 提出无检查边界

- **WHEN** 某提案允许调用不带效应与所有权注解的外部代码，或以类型系统无法检查的方式反射值
- **THEN** 必须依本原则拒绝

### Requirement: 原则 9 —— 单一错误机制

错误必须流经语言中唯一的通知与传播机制。并行通道——异常、隐式 panic 传播、"仅为并发而设"的独立失败路径——不得存在。并发相关失败（超时、取消、任务内部 panic）与一切其他失败使用同一机制。具体机制由本规范的错误处理章节定义。

#### Scenario: 提出并行失败通道

- **WHEN** 某提案引入异常或任何第二条错误传播路径，包括仅限于并发任务域的
- **THEN** 必须依本原则拒绝

### Requirement: 原则 10 —— 完成度闭环优先于超前设计

进入本规范的特性必须同时携带检查、代码生成、运行时行为的完整设计。解析器接受而代码生成器不认识的构造，或通过了检查而没有运行时方案的构造，不得被批准进规范。半成品特性不得以未来会补全为预期交付。

#### Scenario: 半成品特性寻求批准

- **WHEN** 某提案为某构造定义了语法与检查，但留空代码生成或运行时行为
- **THEN** 该提案必须在三要素齐备前暂缓批准

### Requirement: 优先序与决胜

十条原则构成严格优先序：1 局部可推理性、2 唯一语义、3 可判定性、4 消除歧义、5 显式性、6 静态可判定性、7 工具链一致性与机器可操作性、8 不留逃生舱、9 单一错误机制、10 完成度闭环。评估提案时两条原则冲突，序位高者胜。偏离某条原则或偏离本排序，必须在提案的 `## Why` 中显式论证，并以 ADR 记录该例外。

#### Scenario: 提案中原则冲突

- **WHEN** 某提案提升了显式性（原则 5），但以局部可检查性（原则 1）为代价
- **THEN** 原则 1 胜出，该提案必须重做或拒绝；任何例外须经 ADR

### Requirement: 宿主与编译目标策略

We 以可商用语言产品交付：编译器与运行时均为产品面，对性能、效率、资源占用做极致追求。批准的平台承诺为：

- 编译器**从第一天起发射 LLVM IR**，经 LLVM 后端产出原生二进制；工具链以钉住 LLVM 版本为纪律。
- 运行时为自建，属产品范围而非实现细节：包含完整 GC 机制（精确回收）、调度器、I/O 多路复用、本规范定义的并发原语。
- 编译器实现语言是工程选择，与编译目标及语言语义解耦；编译器发射文本 IR 并驱动 LLVM 工具链。
- 外部函数接口为 `foreign "c"`：C ABI 上受控的互操作边界，接受完整的类型、效应、所有权检查（原则 8）。
- 本规范以自身术语定义可观察语义与保证。GC 精确性、暂停预算、尾调用行为是由运行时承载、以基准度量的实现质量目标；仅经显式 spec 层变更才可成为规范承诺。

#### Scenario: 经后端机制定义语言行为

- **WHEN** 某提案以 LLVM 机制、GC 实现或运行时内部来定义可观察语言行为
- **THEN** 必须改写为以自身术语定义可观察行为，或拒绝

#### Scenario: 边界削弱检查

- **WHEN** 某提案以便利或性能为由，要求在 `foreign "c"` 边界逃逸类型、效应、所有权检查
- **THEN** 必须依原则 8（经本条 Requirement 读出）拒绝
