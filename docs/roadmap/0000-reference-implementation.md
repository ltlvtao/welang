# welang Reference Implementation Roadmap

This document is the single authority for reference-toolchain execution state: the strategy, the milestone sequence, and the follow-ups discovered while implementing. It carries no language behavior (that lives in `docs/spec/`), no long-term tradeoffs (those live in `docs/decisions/` — see ADR-0002 for the host and target strategy), and no process rules (`docs/process/development-process.md`).

## Strategy

- **Thin vertical first** (user adjudication, 2026-09-04): reach the minimal end-to-end `we new` → `we check` → `we build` → `we run` early — a minimal front-end subset, LLVM IR emission, a minimal C runtime — then widen every pipeline stage chapter by chapter. This honors ADR-0002's "LLVM IR from day one" and chapter 0's completeness closure in execution order, and buys the earliest honest end-to-end signal.
- **Spec first**: every slice implements ratified chapters; no compiler behavior without a spec basis (development process, invariant list).
- **One change per milestone**: each milestone is one small, vertically verifiable openspec change; its state row below flips in the change that archives it.
- **Self-hosting closes the loop** (user adjudication, 2026-09-08): the bootstrap track (B1–B3) follows the reference milestones and may interleave with the pending M rows — B1 is the critical path and grows out of M10b's multi-function widening; B2 is B1's debugging infrastructure (fs and process faces first); LLVM access rides the existing .ll-text-plus-subprocess-clang architecture, so no LLVM C-API binding sits on the path. ADR-0002 carries the decision.

## Execution state rules

- A milestone's State flips only in the change that archives it; execution state lives only here.
- The sequence after M4 may reorder as widening reveals dependencies; any reorder is a change to this file carried by the affected milestone's change.
- The not-implemented boundary: subcommands this reference build does not run yet report one stderr line and exit 70 (transient implementation state, not a spec surface); the set shrinks to zero as milestones land.

## Registered follow-ups

Items found during implementation that the spec does not fix; each leaves this list only through its own change.

1. **Project-name precise rule.** Chapter 21 R1/R8 and chapter 22 R1 reference "chapter 1's naming convention" for TOML-level names, but chapter 1's naming-conventions requirement fixes identifier case by binding kind only; the concrete charset lives in chapter 22's text and E1904's remediation ("lowercase letters, digits, and hyphens"). A future lexical or toolchain amendment should fix the exact rule (leading or trailing hyphens, length) in chapter 1. Until then the implementation validates: non-empty, charset `[a-z0-9-]` exactly, nothing invented.
2. **Registry embedding.** The compiler hardcodes CLI-level registry titles and remediations at call sites; embedding `diagnostics.toml` (`go:embed`) lands with the first real pipeline stage, when the installed-binary registry question must be answered.
3. **Spec-version label.** `SpecVersion` "0.9.0" (`internal/version`) labels the first canonical baseline after the private v0.8 draft; if a different labeling is adjudicated, the change is one constant plus this row.
4. **Operator type-domain table.** The ratified text names the numeric and Bool operands of the operators chapter 2 accepts, but no requirement fixes the full per-operator domain table (which base types each operator admits at each operand). Until an amendment ratifies the table, same-type operand pairs beyond the ratified numeric/Bool/comparison domains stop at an honest boundary (`arithmetic and comparisons beyond the ratified numeric and Bool domains (spec gap; roadmap follow-up)`); disagreeing operands stay E0501. Found by M3 (`types-and-main` design D4).
5. **Call argument-count and non-function-callee diagnostics.** No ratified requirement fixes the diagnostic when a call's argument count differs from the callee's declaration, or when the callee is not a function. Until an amendment claims the codes, both stop at honest boundaries (`calls with an argument count the callee does not declare (spec gap; roadmap follow-up)`, `calls on values that are not functions (spec gap; roadmap follow-up)`). Found by M3 (`types-and-main` design D10).
6. **Single-file build artifact naming.** Chapter 21 R2 says the build artifact is named by the manifest, but a single-file compile (the `[path]` file form R1 fixes) has no manifest to name an artifact. Until a toolchain amendment fixes the single-file artifact's name and place, `we build <file>.we` / `we run <file>.we` run the full pipeline first (diagnostics report as usual) and stop at an honest boundary (`single-file builds (spec gap; roadmap follow-up)`). Found by M4 (`native-vertical`, adjudication Q3).
7. **Assignment-target mutability.** No ratified requirement fixes the rule or diagnostic when a `let`-bound name is reassigned (`let x = 1; x = 2`); chapter 8's ownership text fixes categories for captures, not reassignment of a non-`var` binding. Until an amendment claims it, the implementation keeps M3's behavior (the assignment type-checks against the binding's type). Found by M5 (`control-and-composites` design D14).
8. **Registry E0604 stale clause.** E0604's registry description carries "a member access names an undeclared field / Fires under: Field access", which conflicts with chapter 8 R5's routing (unknown names on records are E0816, "one rule, one code"); the chapter text is the trigger-semantics authority and M5 emits E0816 there. The stale clause's cleanup belongs to the next change that touches `diagnostics.toml` (or a dedicated maintenance change). Found by M5 (`control-and-composites` design D10).
9. **`we run` path resolution from outside the project directory.** `we run <path>` sets the child process's working directory to the project path but resolves the artifact by its relative path, so invoking from outside the project directory fails with `fork/exec … no such file or directory`; invoking from inside (`we run .`, the conformance runner's style) works. A toolchain fix should resolve the artifact against the invocation directory before changing the child's cwd. Found by M5 (`control-and-composites` T7 observation; M4 legacy, `internal/cli` untouched by M5).
10. **Newtype in the Shareable set.** Chapter 18's closed set names base types, the unit type, value records over Shareable fields, value sums over Shareable payloads, tuples, and the eleven synchronized gc types — it does not name a byval newtype over a Shareable underlying type, and chapter 8's category derivations do not extend to the marker. Until an amendment ratifies inclusion, the implementation keeps the literal reading: a newtype is not Shareable, whatever its category. Found by M9a (`concurrency-check` design D3, T5 disclosure).
11. **Runtime structures without reclamation.** Chapter 18 fixes no destruction or finalization semantics for the runtime's own structures — scheduler tasks and stacks, scope frames, wait-chain nodes (including select losers left for lazy reaping), panic reports, and runtime-generated bitmaps — so the M9b run tower allocates them from the malloc family and never reclaims: the leak is bounded by the task and registration counts and lives for the process lifetime. A future runtime change (reclamation passes, or a finalizer mechanism — behind ADR-0003's parallelism gate) should claim it. Found by M9b (`concurrency-run` design D7, D13 disclosure 2).
12. **Test-module importability versus the module-path charset.** Chapter 21's scenario calls `src/helpers_test.we` "compiled with the project, importable" — but the import→file mapping (chapter 15) spells module paths from `[a-z][a-z0-9]`-shaped segments (E0013 as implemented), and an underscore stem cannot be spelled; the project compilation walks the import graph from src/main.we, so a test module outside it never compiles under `we check .`. Either the charset admits the underscore stem or the scenario's importability needs its own mapping — a spec amendment should fix which. Found by M10a (`testing-check` design D10; Q1 split's loader-boundary disclosure).
13. **The test keyword versus the std.test module segment.** Chapter 1's reserved-word closure makes `test` a keyword (it heads the test-block production), so the segment cannot lex as an identifier; chapter 15's qualified reach is exactly `name.item` through an import's name, and the chapter 20 examples call `std.test.assertEqual(...)` — a two-level dotted form chapter 15 does not fix. M10a makes the ratified surface spellable (module-path segments accept keyword tokens passing the charset check) and serves calls through the alias form (`import std.test as st; st.assertEqual(...)`); the bare import binds the keyword name and is inert. A spec amendment should fix which call surface is real: the two-level std qualifier, alias-only examples, or a non-keyword module name. Found by M10a (`testing-check` design D8, implementation-prep disclosure).
14. **Mock targets among the concurrency constructors.** Chapter 20's unmockable-target requirement rejects a generic fn, an impl method, or "a constructor such as `User`" with `E1804:` — the concurrency constructors are not named. M10a's literal reading accepts `mock conc.channel` at the check face (the name resolves to a module-level fn entry, so no special case fires, `m10a_test.go:178`), but the run face is a primitive-constructor face: channel construction derives its expected types from the call's own arguments, not from a declarable signature, and the only restatable signature (no parameters, unit return) has nothing to intercept. M10b keeps the check face unchanged and leaves channels out of the slot table — a checked `mock conc.channel` runs the real constructor at runtime. An amendment should adjudicate the reclassification: either E1804's set names the primitive constructors (the check face rejects what the run face cannot honor), or the chapter fixes an interception surface for them. Found by M10a (`testing-check` review F1), registered with M10b (`testing-run` design D3).
15. **Chapter 19's second effect-segment example spelling.** Chapter 19's foreign-declaration requirement shows the signature forms as `fn name(params) effect tag1 tag2 ...` or `fn name(params) -> type effect tag1 tag2 ...`; the second literal example places the segment after the return type, contradicting the same sentence's own prose ("between the parameter list and the arrow or the declaration's end") and the binding authorities — chapter 6 ("between the parameter list and the arrow or body") and chapter 16 ("between the parameter list and the arrow (or the body, when no return type is written)"). Prose-level typo in the example, not a semantic conflict: the M12 implementation and its golden matrix spell foreign declarations per chapters 6/16 (`fn name(params) effect tags -> type`). A spec change should correct the chapter 19 example. Found by M12 (`ffi` T1 golden-source probes, disclosure 1).
16. **Codegen dominance defect: match-with-assignment before a scope block.** *(Closed by B1a — the fix landed with the widening this row anticipated.)* In one function, a match statement whose arms assign, executed before a `scope` (including `scope timeout`) block, emitted IR that violates dominance — clang rejected with `Instruction does not dominate all uses`; the reference-build workaround (deferring the first match to after the scope) shapes M15's errpath-02 reference solution and is disclosed in its traps.md. B1a fixes it at the root: the arm-scoped frame snapshot (T1) and the value-position classification's arm join (T13) emit IR clang accepts, pinned by the T14 battery's `b9-dominance` probe (clang exit 0, no "does not dominate"). The number is retained so the in-tree citations (`internal/codegen/codegen.go:473`, `:4368`, `:6582`, `internal/codegen/envframe_test.go:10`, the errpath-02 and ctxpass-02 `traps.md` notes) keep their referent. Found by M15 (`benchmarks`, implementation disclosure 2).
17. **Evaluation suite: real-batch face and L2/L3 expansion.** M15 lands the methodology, the 18-task L1 seed set, and the in-process runner self-certified by synthetic batches. Still owed: real LLM batch production (the production face, separate from judging by design), the wall-clock guard for non-terminating attempts (the in-process runner halts on a busy loop with no wait source — the one shape deadlock detection cannot see), and L2 (module-level) / L3 (system-level) task expansion. Found by M15 (`benchmarks`, non-goals and runner disclosure).
18. **Chapter 7 fixes no rounding or sign convention for `/` and `%`.** The chapter's arithmetic requirement covers the checked `+ - *` family alone; for the two remaining integer operators it fixes neither the quotient's rounding direction nor the remainder's sign when an operand is negative. The reference build keeps the truncating reading (LLVM's `sdiv`/`srem`: the quotient truncates toward zero, the remainder takes the dividend's sign) — the convention Rust and C fix — and discloses it where the emission is described (the codegen-mono change, design D2). A types-chapter amendment should ratify the convention or replace it. Found by B1a codegen-mono (T3, ruling of 2026-09-10).
19. **Division by zero has no clause anywhere in the specification.** Chapter 7's checked-arithmetic requirement names overflow alone, and the constant folder declines an undefined evaluation rather than reporting one (`foldApply`'s `/` and `%` branches return not-ok), so a literal `10 / 0` checks clean and reaches the runtime. The reference build traps there — a `panic` with `division by zero` through chapter 14's mechanism, the only capture face such a program has — which is the reading chapter 7's "checked; it MUST NOT silently wrap" posture implies but does not state. An amendment should fix whether division by zero is a runtime trap, a compile-time error when constant-evaluable, or a third thing. Found by B1a codegen-mono (T3, ruling of 2026-09-10).
20. **Out-of-range and overflowing shift semantics.** Chapter 7 fixes no behavior for a shift amount at or past the operand width, or negative, and LLVM's shift instruction is poison there, so the emitter must choose. The reference build traps, naming the operand's declared integer type (`Int8 shift overflow`, `Int64 shift overflow`), and for `<<` also traps when a bit would leave the top — the checked reading the chapter's no-silent-wrap rule implies, since LLVM's `shl` discards those bits without a word. An amendment should ratify the range rule and whether a left shift's lost bits count as an overflow. Found by B1a codegen-mono (T3, ruling of 2026-09-10).
21. **String buffers without reclamation.** Chapter 18 fixes no destruction or finalization semantics for a String's bytes, and no clause elsewhere says who may reclaim them. The reference build's String family allocates every buffer with `malloc` outside the gc domain — a raw byte buffer is not a gc object (no header, no descriptor), so a non-gc pointer on the shadow root stack would be read as a block header by the collector — and never reclaims: the leak is bounded by the program's own string-building volume and lives for the process lifetime, which is also why the family's `byteSlice` may hand back an interior pointer. Reclamation belongs with the allocator work ADR-0003 gates. Found by B1a codegen-mono (T4, ruling of 2026-09-10).
22. **Full-width unsigned arithmetic is read as signed.** Chapter 7's arithmetic is checked against the declared width, and the reference build answers that question with LLVM's `sadd`/`ssub`/`smul.with.overflow.i64` intrinsics — a *signed* reading of the i64 register. The six widths narrower than the register are checked by a range test against their own bounds (codegen-mono T11); `UInt64`, which IS the register, admits no such test, because a sum past 2^64-1 wraps to a value inside the range while the intrinsic's sign flag does not mean carry. Today `18446744073709551615u64 + 1u64` silently wraps to 0, and a legal exact sum at 2^63 is misreported as `Int64 add overflow`. The width's own check needs an unsigned idiom (LLVM's `uadd`/`usub`/`umul.with.overflow` family, or a comparison against the operands), and an amendment should ratify what the chapter's no-silent-wrap rule demands where the register's arithmetic and the declared width coincide. Found by B1a codegen-mono (T11, ruling of 2026-09-11).
23. **Interpolation holes are not type-checked.** Chapter 1's "No implicit conversion" and chapter 7's call-argument requirement hold at every call site except inside a `${…}` hole: no file under `internal/typecheck` reads the hole list the parser builds (`ast.Literal.Holes`), so `"${one(true)}"` — a `Bool` argument for an `Int64` parameter — checks clean, builds, and runs, printing `1`, while the same call outside the hole is E0501 ("no coercion is ever inserted"). The B1a widening is what made the shape reachable: before it, every hole stopped at the codegen boundary (exit 70). The root cause is a recorded T4-era ruling (the parser builds the hole AST and the checker deliberately does not type it), so the remedy is an adjudication, not a patch: type the holes, re-check a call's argument domains against the callee's signature at the emit site, or declare the gap in `docs/` explicitly. Found by B1a codegen-mono (T14 verification battery, finding N3).
24. **A resource handed to an open generic position leaves its release discipline.** Chapter 8's resource rules make a binding's transfer the only sanctioned exit, and E1104's remediation names three: `scope resource(x = v)`, `return v`, or passing it to a function whose parameter declares the type. The resource walker's call arm (`internal/typecheck/resource.go:431-440`) kills a live resource argument on *any* call — "the argument hands the handle to the callee's signature" — without ever checking that the callee's parameter declares the resource type, so an open position `T` accepts the handle: the callee side has no release obligation (nothing is released, on any path) and the construction site's argument type is the position rather than the resource, so the E1106 that rejects every direct boxing route never fires. The gap is independent of `Dyn` — `fn width<T>(v: T) -> Int64` called with a `byres` value checks clean and elides the release with no box in the program — and the discipline itself is real for concrete parameters (`fn width(v: FileHandle) -> Int64` is E1104), so what is missing is the discharge of that rule at an open position. B1b codegen-full (T5's blocked-prerequisite investigation) makes the boxing consequence reachable: `fn boxed<T>(v: T) -> Dyn<Describe> where T: Describe { return Dyn<Describe>(v) }` called with a resource emits a box holding the handle. Which layer owes the check (a parameter-type test in the walker, a re-check after instantiation, or a separate rule at the `Dyn` construction site) is the amendment's to fix. Found by B1b codegen-full (T5, ruling of 2026-09-12).
