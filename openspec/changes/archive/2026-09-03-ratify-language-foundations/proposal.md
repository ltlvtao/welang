# Proposal: ratify-language-foundations

## Why

从头建立策略（`refr/spec-0.8.md` 仅作方向性参考，不作基线）意味着：spec-0.8 中的每一个既有决定都从"结论"降级为"待裁决项"。待裁决项本身不可怕，问题在于**裁决需要标准，而标准目前不存在于仓库内**：

1. **最高裁决依据没有可入库的权威文本。** `AGENTS.md` 将"十条设计原则"声明为一切语言取舍的最高裁决依据，但这十条原则的定义、优先序与适用边界只存在于 `refr/`（永不入库）。`welang-spec-impact-audit` 的"原则一致性"检查将被迫依赖私有参考材料。
2. **原则未经本项目批准。** spec-0.8 的十条是草案作者的候选清单，不是我们论证后的裁决规则。作为口号它们成立；作为裁决规则它们不完整——缺少优先序的决胜语义，缺少真实冲突下的裁决示例，无法对具体设计争议作出可预期的判定。
3. **价值源头是隐含前提。** 十条原则共同服务于一个未被显式声明的前提：We 的第一作者是 LLM，编译器是裁决者，人是审计者。不把这个前提变成显式决定，原则的推导链条就是悬空的。

本变更是后续任何语言内容变更得以通过审计的前置条件。

## 目标与非目标

目标：

1. 显式批准两项基础决定：
   - **第一公民与核心循环**：We 为"生成—检查—修复"循环中的 LLM 优化；人类的角色是审计与裁决，不是逐行编写。
   - **带优先序的设计原则集**：作为一切后续语言取舍的裁决规则。
2. 每条原则以**可裁决形态**成文：定义、优先位置、裁决语义（它裁决什么、何时让位）、至少一个真实设计冲突的裁决示例。
3. 通过归档提升创建 `docs/spec/0000-principles.md`（规范第 0 章），作为 `docs/spec/` 的第一个内容。
4. 将 `AGENTS.md` 中的原则内联清单改为指向规范权威（"一类事实只有一个权威位置"）。

非目标：

- 不操作化 AI 原生判据（First-Pass Compile Rate、修复循环收敛、潜伏缺陷率等）——那是独立的 benchmark 层变更。
- 不做任何语言行为/特性决定（类型系统、错误处理、效应系统、并发模型……均属后续内容变更）。
- 不搬运或翻译 spec-0.8 中原则章节之外的任何内容。
- 不修改研发流程机制本身（仅补充"规范增量书写语言"的约定澄清）。

## What Changes

- 新增规范能力 `language-foundations`，全部为 ADDED Requirements，包含：
  - **第一公民与核心循环**：LLM 生成、编译器裁决、人审计的分工；由此推导出的基本取向（如：为局部可推理性牺牲简洁性、诊断信息是第一接口）。
  - **设计原则集与优先序**：候选集取自 spec-0.8 的十条（局部可推理、唯一语义、可判定性、消除歧义、显式优先、静态可判定、工具链一致性、不留逃生舱、单一错误机制、完成度闭环），逐条改写为可裁决条款，并规定优先序决胜语义（冲突时高位者胜；例外必须显式论证并以 ADR 记录）。
  - **宿主与编译目标策略**（用户裁决 2026-09-03，经两轮讨论细化）：We 的目标是**可商用交付的语言**——编译器与运行时均为产品，对性能、效率、资源占用做极致追求（v0.8 规范曾有 demo 实现，属试用版；本仓库为商用级从头重建）。编译目标为 **LLVM：从第一天起生成 LLVM IR**，经 LLVM 后端产出原生二进制（钉 LLVM 版本为工具链纪律）。运行时为自建，包含**完整 GC 机制**（精确回收）、调度器、I/O 多路复用、Channel/Shared 原语——这是为商用目标明确接受的成本。编译器实现语言为 Go，以文本 IR 发射 + 调用 LLVM 工具链的方式协作，与编译目标**解耦**。FFI 为 `foreign "c"`——C ABI 受控互操作边界（类型、effect、所有权全检查）。规范纪律：语言语义与可观察保证由 We 自行定义；精确 GC、暂停预算、尾调用等属实现质量目标，由 runtime 承载并以基准度量，是否升格为规范承诺留待后续 spec 层变更显式决定。此决定推翻 v0.8 的 Go 后端策略（`foreign "go"`、`runtime.We*` 映射表不再采纳）。
- 修订 `AGENTS.md` 语言研发不变量：原则内联清单改为指向 `docs/spec/0000-principles.md`。
- **文档与目录命名约定（新）**，三条规则，权威表述记入 `docs/README.md`：
  - **设计语料用位置编号**：`docs/spec/` 章节文件为 `<nnnn>-<slug>.md`（四位零填充、步长 100，相邻编号间可插入而不重排；`0000` 保留给规范第 0 章）；ADR 为 `ADR-<nnnn>-<slug>.md`。
  - **只追加账本用单调编号或日期**：归档变更目录移入 `archive/` 时改名为 `YYYY-MM-DD-<name>`——日期即时间序，无需并发协调，且 `validate.py` 不校验 `archive/`，机械兼容。
  - **语义身份用语义名**：active 变更目录与 `specs/<capability>/` 能力名保持 kebab 语义名——变更名是跨工件引用的连接键，能力到章节文件的映射在归档提升时决定，不提前焊死。
  - 固定结构名（`README.md`、`AGENTS.md`、`SKILL.md`、`change.yaml` 及 openspec 四件套文件名）不参与任何编号——工具与跨工具约定依赖这些名字。
- 语言约定澄清（小改动）：规范增量 `specs/*/spec.md` 使用**英文**书写——它们是 `docs/spec/` 英文权威文本的字面片段，归档提升时应可逐字合并；`AGENTS.md` 硬规则 2 与 `docs/process/development-process.md` §3.3 各补充一句。

ready 阶段必须解决的开放问题（初步清单，spec-impact audit 时逐项核销）：

1. ~~优先序是否维持 spec-0.8 的排序~~ **已裁决（2026-09-03，用户确认）**：维持 spec-0.8 原序不变。"显式优先"与"静态可判定"不互换（找不到序位起决定作用的真实冲突对）；"工具链一致性"不拆分（两款义务同服一个循环）。论证见 design 决策 2。
2. ~~每条原则的裁决示例~~ **已裁决（2026-09-03，用户确认）**：每条原则一个 Scenario，标准为"真实可能出现的提案形态 + 单靠本原则即可裁决"；P2/P5/P7 因有两条独立裁决路径各配两个。淘汰的耦合示例（宏 vs 工具链一致性、`any` vs 不留逃生舱）不入正文。见 design 决策 3。
3. ~~FFI 定位~~ **已裁决（2026-09-03）**：`foreign "c"`，C ABI 受控互操作边界；Go 后端不再作为参考目标（如未来需要 Go 生态互操作，经 C 桥另议）。"不留逃生舱"条款的表述以"受控边界 + 全检查"为准。

## 影响层

- **spec**：创建规范第 0 章（`docs/spec/0000-principles.md`，归档提升时生成）。此后所有 spec 层变更获得其审计所引用的裁决依据；本层变更是 `docs/spec/` 的起点。
- **process**：`AGENTS.md` 不变量一节由内联清单改为指针；不变量"编译器实现语言为 Go（与代码生成目标一致）"改为解耦表述（实现语言 Go；编译目标 LLVM → 原生二进制，见规范第 0 章）；语言约定补充"规范增量用英文"规则（`AGENTS.md` + `development-process.md` 各一句）；归档流程同步日期前缀规则（`development-process.md` §7、`openspec/README.md` 归档小节、`.agents/skills/welang-archive-sync/SKILL.md` 各补一句：移入 `archive/` 时目录名加 `YYYY-MM-DD-` 前缀）。
- **docs**：`docs/README.md` 新增"文档命名约定"一节（四位前缀 + 步长 100 + 固定结构名豁免清单）；`docs/process/development-process.md` §7 的 ADR 命名同步为 `ADR-<nnnn>-<slug>.md`。

## 影响范围

- **所有后续变更**：规范影响审计与变更评审从此引用规范内原则；与原则冲突的提案必须在 proposal 中显式论证并以 ADR 记录（`AGENTS.md` 既有规则，因本变更而落地）。
- **与 spec-0.8 的关系**：宿主策略（Go 后端、`foreign "go"`、类型映射表）被本决定推翻，v0.8 相应内容仅作反例参考；其余内容仍为方向性参考。商用目标下，自建运行时（精确 GC、调度器、netpoll、并发原语）与 LLVM 后端为**既定产品范围**而非临时代价；被拒路线（Go 后端、C 源码中间层）以 ADR 记录。评估基准（First-Pass Compile Rate 等）作为质量门继续适用，评估重心在前端与诊断闭环（`we check` 不依赖代码生成）。
- **不受影响**：编译器/标准库/工具链代码（尚不存在）；评估基准定义（独立的 benchmark 层变更）；研发流程的状态机与关卡机制。
- **风险与不可逆性**：优先序是全仓库被引用最多、最难反悔的决定（反悔会使已积累决策的论证基础作废）。本变更刻意选择"代码量为零、杠杆最大"的第一刀；所有实质争议都必须在 ready 前收敛。
