# Design: ratify-language-foundations

## 决策 1：十条原则全部采纳自 spec-0.8 §2，但改写为机制中性

候选集维持十条不变（见 `refr/spec-0.8.md` §2，本变更的固定参考基线），但正文做了"去机制化"改写：

- P9 不再点名 `Result<T,E>` 与 `?`——错误机制的**具体形态**属错误处理章节的内容决定，第 0 章只裁决"**只有一条通道、不得存在并行通道**"。v0.8 把特性名写进原则，是从头重建下不再成立的层次混淆。
- P4 不再点名"软关键字"——词法机制属词法章节；第 0 章只裁决"上下文敏感的词法不得引入；例外必须在词法章节闭集枚举"。
- P1 的例外从 `we.toml` 泛化为"项目级构建配置文件"，并收紧为"只影响诊断级行为，不得改变类型/效应/所有权检查的结果"——构建配置的具体形态同样是后续内容决定。
- P7 维持一条原则两款（强制不可配置的格式化器；诊断必须尽可能附结构化机器可操作修复描述）。曾考虑拆成两条，拒绝：两款义务同服一个对象——generate–check–fix 循环的基础设施——拆开不会产生新的裁决情形，只会稀释"十条"这个引用键。

每条原则的可裁决四要素：**定义**（MUST/MUST NOT 正文）、**优先位置**（Priority order Requirement 中的序号）、**裁决语义**（正文即裁决规则 + 例外条款显式列出）、**裁决示例**（Scenario，见决策 3）。

## 决策 2：优先序维持 spec-0.8 原序

主张（供评审裁决）：`1 局部可推理 → 2 唯一语义 → 3 可判定性 → 4 消除歧义 → 5 显式 → 6 静态可判定 → 7 工具链一致性 → 8 不留逃生舱 → 9 单一错误机制 → 10 完成度闭环`。

论证：

- 该排序在 v0.8 的 2665 行规范里被一致地使用过一遍，内部自洽；从头重建推翻它需要理由，而候选理由都不成立。
- 考虑过的调整及拒绝理由：
  - **P5/P6 互换**（显式与静态可判定谁更高）：找不到一个真实冲突对里序位起决定作用——显式性与静态可判定性在实践中同向（越显式越可静态判定），冲突情形由 P1/P3 更高位者先裁决。无实际裁决力的排序争议不值得动。
  - **P7 拆分**：见决策 1 末款。
- 决胜语义成文：冲突时高位者胜；突破原则或突破排序，须在 proposal `## Why` 显式论证 + ADR 记录（与 `AGENTS.md` 既有规则对齐，本变更使其落地）。
- 排序中相邻两条主语不同质（P1–P2 裁决"信息可用性"，P3–P6 裁决"检查行为"，P7 裁决"工具面"，P8–P10 裁决"语言边界与交付纪律"），这也是原序合理的佐证：分组内部无冲突时无需排序发力。

## 决策 3：裁决示例的选择标准

每条原则至少一个 Scenario，入选标准：**必须是真实可能出现的提案形态**（v0.8 演化或后续变更里 foreseeable），不是稻草人；示例必须单靠该原则即可裁决（不与其他原则耦合，否则示例失去教学与裁决双重价值）。P2、P5、P7 配两个 Scenario，因为它们有两条独立裁决路径（P2：重复路径 / 划分规则主观；P5：无锚点 / 锚点但开类；P7：格式化器可配置 / 诊断缺机器可操作形态）。

淘汰的候选示例："宏 vs 工具链一致性"（实际由 P3 与 P7 各裁决一半，耦合，弃用）、"`any` vs 不留逃生舱"（实为 P8 直接适用，但 P6 也部分适用，改为 P8 的无检查边界示例更纯）。

## 决策 4：定位（目标场景）作为第 0 章第一个 Requirement

v0.8 §1 的目标域（HTTP/RPC、后台任务、CLI、数据管道）与非目标域（内核/驱动/嵌入式/游戏引擎/HPC）是一切取舍的**前提**而非原则之一——它不参与优先序决胜，而是优先序的适用域。独立成 Requirement 置于最前，使其可被后续 spec 层变更显式修订（修订定位是比修订原则更重的决定，但机制相同）。

## 决策 5：宿主与编译目标策略放第 0 章，不另立章节、不放编译器文档

- 放第 0 章：该决定含一条**规范书写纪律**（"语言行为不得以 LLVM/GC 机制定义，必须以可观察语义定义；实现质量目标升格为规范承诺须走显式 spec 变更"）——它约束所有后续 spec 层变更的写法，属宪法级，必须在裁决依据章内。
- 拒绝另立 `0050-host-strategy` 章节：拆散宪法会让"审计引用裁决依据"退化为跨章拼装；且 LLVM/GC 的**产品承诺**与**规范纪律**本就一体。
- 拒绝放编译器文档：无法约束 spec 层变更的书写。
- 同时第 0 章只写策略与纪律，不写实现细节（IR 具体形态、GC 算法、调度器设计——它们属于后续 compiler 层变更与 ADR）。

## 决策 6：第 0 章不含具体语言特性

Result、`?`、Shared、effect 名单、诊断码、`we.toml`、软关键字……一律不出现（v0.8 原则章节里出现过的按决策 1 中性化）。判据：第 0 章的每个条款必须能独立于任何后续章节被引用来裁决争议；点名特性即制造对未裁决章节的隐含承诺。ADR-0002（宿主策略）在归档时创建，被拒路线（Go 后端、C 源码中间层）入 ADR 而不入规范正文。

## 决策 7：诊断码——本变更新增零个

本变更只产出裁决规则，不定义任何诊断行为，故无新增诊断码（审计点 3 的显式回答）。后续章节的歧义诊断（P4 Scenario 提及的 ambiguity diagnostic）届时由词法/语法章节定义编码。

## 决策 8：提升与校验方式

归档提升时：`specs/language-foundations/spec.md` 的 ADDED Requirements **逐字合并**为 `docs/spec/0000-principles.md`（去掉 delta 头 `# language-foundations Specification Delta` 与 `## ADDED Requirements`，正文原样），并产出配对翻译 `0000-principles.zh.md`。校验：`validate.py --all --strict`（结构）+ `docs_sync.py --root docs`（配对与结构同步）+ 人工术语一致性审查（local reasonability / unique semantics / escape hatch 等关键术语的跨文件统一，英中对照表随翻译一并产出）。"逐字可合并"正是规范增量用英文书写的动因（proposal 的语言约定澄清项）。
