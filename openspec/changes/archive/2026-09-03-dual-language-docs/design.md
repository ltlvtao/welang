# Design: dual-language-docs

## 决策 1：布局——同目录兄弟文件 `<basename>.zh.md`

选定：翻译与源文件同目录，文件名仅在末尾追加 `.zh.md`，继承源文件全部命名元素（四位数字前缀、ADR 编号）。

被拒方案：

- **平行树**（`docs/` + `docs-zh/` 镜像）：路径双倍维护；所有链接目标需跨树改写；配对关系依赖两层目录的隐式对应，孤儿风险更高。
- **单文件双语**（同文件内中英交替）：无法按语言独立渲染（GitHub 无原生支持）；diff 噪声大；引用锚点混乱。

## 决策 2：英文权威（用户裁决 2026-09-03）

- 规范增量以英文书写、归档时逐字合并为英文正典；中文是同步渲染。冲突时以英文为准，翻译缺陷在引入分歧的同一变更内修复。
- 与已定规则同向：规范增量=英文片段、commit 英文。避免中文正典与英文标识符/诊断术语脱节，也使推广路径（delta 逐字合并）不经过翻译环节。

## 决策 3：结构同步的机械边界

`docs_sync.py` 只做结构代理检测：配对存在性（缺翻译/孤儿翻译）、标题层级计数、围栏代码块计数。它抓不住语义漂移（译错但结构对）——语义等价由 change-review / code-review 承担。这是明确接受的成本，不用脚本伪装解决。

实现要点：

- 纯 Python 标准库，与 `validate.py` 同风格（逐行 FAIL + 汇总行；OK + 退出 0）。
- `--root <dir>` 参数（默认仓库 `docs/`），使夹具测试不触碰仓库工作区。
- **两遍解析**：先按 `^``` ` 行切出围栏区，围栏**外**才做标题识别 `^#{1,6}\s`——否则围栏内 `#` 注释行会被误计为标题，而翻译版可能翻译示例内注释，制造误报。围栏本身按行计数对齐即可，不解析内容。
- 已知局限（接受）：四个反引号嵌套围栏与 4 空格缩进代码块不特殊处理；本项目文档不使用这两者。

## 决策 4：非语言能力增量的推广归档路径

本变更的 `specs/docs-language/` 是**项目能力**而非语言行为能力。归档提升目标不是 `docs/spec/`（语言正典），而是 proposal 声明的权威位置——`docs/README.md` 的 "Documentation language" 章节。为此 `development-process.md` §7 增补一句：语言行为能力提升到 `docs/spec/`，其他能力提升到 proposal 声明的权威位置。"一类事实只有一个权威位置"在推广阶段继续成立。

## 决策 5：docs_sync.py 不并入 validate.py

两者职责不同（变更工件结构 vs 文档双语结构）、触发条件不同（按变更状态 vs 按 docs diff）、失败语义不同。分开维护，各占验证阶梯一行。合并会让"只改文档也要跑变更校验"成为噪音。

## 验证策略

- 负向（夹具，`/tmp` 下构造）：缺配对、标题层级数不一致、围栏块数不一致、孤儿翻译——各退出 1 且输出对应 FAIL 行。
- 正向：仓库终态全绿（两个翻译落地后 `docs_sync.py` 退出 0）。
- 全量关卡：`validate.py --all --strict` + `docs_sync.py` + `git diff --check`。

## 不变量与风险

- 不改变任何语言行为；不涉及诊断码。
- 风险 1：语义漂移超出结构检测能力——由评审纪律承担（完成定义阻塞 `complete`）。
- 风险 2：翻译滞后——同一变更内强制同步，未同步不得勾选对应任务。
